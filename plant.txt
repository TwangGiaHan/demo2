Được. Với thông tin mới này, mình sẽ reset lại thiết kế theo đúng TO-BE Uniform Process, không dùng bản Gift/Uniform trước đó làm baseline nữa.
Điểm quan trọng là Uniform lần này không chỉ là một form CRUD. Nó có 3 lớp nghiệp vụ:
Operator/Employee Registration — public/mobile-friendly form.
Intranet Portal — Admin/GA quản lý request, approval, stock, delivery.
AI Agent Automation — tự động gom request → validate → submit approval → lấy approval → thông báo → theo dõi delivery.
Ngoài ra, mình sẽ bám theo stack bạn đưa:
Frontend:
React + TypeScript
webroot/app/pages
├── master/       # Admin / dashboard / management
└── operator/     # Employee registration

Backend:
PHP
├── Controller
├── Model
└── Shell         # scheduled/automatic jobs

Integration:
Intranet / mySingle / Mail / Knox Mail

Ảnh hiện tại cũng cho thấy hệ thống cũ đang có các trường như Requester Name, Requester GEN, Department, Cost Center, Type, Category, Print Name, Size, Reason, Code, Current Stock, Pending, Price, Order Quantity; đây là cơ sở để mapping từ AS-IS sang TO-BE. Ảnh giao diện mới lại định hướng rõ hơn về đăng ký đồng phục, bảng size và tiêu chuẩn phát, trong đó bảng Ghile, Áo Thun nam/nữ và Pregnancy được hiển thị ngay trên trang.

3. BUSINESS RULES
Đây là phần quan trọng nhất để code.
BR-001 — Annual General Allocation

General employee:
1 pc / year


BR-002 — New Hire
Indirect
New hire
→ 2 Ghile

Direct
New hire
→ 3 T-shirt

Theo requirement hiện tại:
IF Type = Ghile
AND Reason = New Hire
THEN Qty = 2

IF Type = T-shirt
AND Reason = New Hire
THEN Qty = 3

Reason = Maternity
→ Quantity = 2

└── Week 24
    └── Pink

18. AI AGENT — NÊN DÙNG AI Ở ĐÂU?
Một điểm mình rất khuyến nghị:

Ví dụ không nên:
LLM tự suy luận:
"Employee này chắc được 2 áo"

Mà phải:
PHP Rule Engine
       ↓
Quantity = 2

AI Agent chỉ orchestrate:
AI Agent
   │
   ├── Get requests
   ├── Call validation service
   ├── Group department
   ├── Generate approval content
   ├── Submit
   ├── Read approval result
   └── Send notification

Business Rule
Nên để deterministic:
Policy Engine

AI
Nên dùng cho:
Generate approval email.
Generate notification.
Summarize rejected requests.
Explain validation error.
Detect unusual request pattern nếu cần.

28. ĐIỂM CẦN CHỐT TRƯỚC KHI CODE
Có 7 điểm mình không khuyên developer tự đoán.
1. Direct / Indirect
Hiện requirement:
New hire
Indirect → 2 Ghile
Direct → 3 T-shirt

Cần xác định employee master field nào xác định Direct/Indirect.

2. Maternity
Cần chốt:
Maternity = 2

có phải 2 request riêng không?

1 Parent Request
    ├── Allocation Week 11
    └── Allocation Week 24


3. Current Stock vs Pending
Cần chốt:
Available =
Current Stock - Pending

hay:
Available =
Current Stock - Pending - Reserved

Mình khuyến nghị phương án thứ hai.

4. Approval timing
Cần chốt chính xác:
Monday
→ collect

hay:
2 times/month

và ngày cụ thể.

5. "GA warehouse Thursday"
Cần chốt:
Thursday = Admin receives stock

hay:
Thursday = Employee receives stock

Requirement hiện tại đang mô tả cả hai khái niệm.

6. Received evidence
Cần chốt evidence là:
Button "Received"
+
Datetime

hay:
Button
+
Photo

Requirement hiện tại nói date/time là evidence, còn Admin cần upload evidence.

Đây là điểm kỹ thuật cần đặc biệt chú ý.

thì bất kỳ ai biết GEN ID đều có thể tạo request.
